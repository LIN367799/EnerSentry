## 零、读前必看：用大白话讲清储能电站

> 这一章的目标：读完你就能看懂后面所有内容，不需要任何电池专业背景。

### 0.1 先建立一个最核心的类比

**储能电站，本质上就是一个"超大号充电宝"。**

你手机里的充电宝：里面有几节电池，能充电、能放电，有一个电路告诉你还剩多少电。储能电站做的全是同一件事，只是**体量放大了几万倍、安全要求严了几百倍**：

- 手机充电宝：几千毫安时，几瓦；
- 一个储能电站：几万度电，几兆瓦（百万瓦）功率，够一个小片区用一阵子。

既然是"充电宝"，它里面就一定有**电池**。问题来了：一个电站有**上万节**电池，怎么管？这就是本项目的全部出发点。

### 0.2 从"一节电池"开始，一层层叠起来

电池不是一整块造出来的，而是像搭积木一样从小到大拼起来的。记住这个**四层嵌套**，后面反复用到：

```
储能电站
 └── 电池舱 Container × N      （一个集装箱大小的房间，排成一排）
      └── 电池簇 Rack × M       （舱里立着几个高柜，像服务器机柜）
           └── 电池包 Pack × K   （柜子里一层层的"电池模块"）
                └── 电芯 Cell × 100+  （最小的电池单体，一切的起点）
```

一句句翻译成人话：

| 层级 | 大白话 | 生活类比 |
|------|--------|---------|
| **电芯 Cell** | 一节锂电池单体，比如磷酸铁锂单体约 3.2V。又大又贵又危险 | 像手电筒里的**一节 5 号电池**（只不过大几十倍） |
| **电池包 Pack** | 把几十~上百节电芯用导线串/并联，装进一个金属壳，做成一个"电池模块"，几百伏 | 像把很多节电池**捆成一个大电池块** |
| **电池簇 Rack** | 把十几个电池包竖直叠起来，塞进一个高柜（像服务器机柜） | 像把很多大电池块**叠成一个高柜子** |
| **电池舱 Container** | 一个集装箱，里面塞进几簇，再加空调、消防 | 像把几个高柜**装进一个集装箱房间** |

> 为什么串/并联？**串联**是为了把电压"叠高"（几十节 3.2V 串起来才有几百伏），**并联**是为了把容量"摊大"（同样的电压下存更多电）。

**规模感**：一个电池舱里可能有 **1 万节以上**电芯。每一节都要被测电压、测温度。

### 0.3 两个关键"管家"：BMS 和 PCS

光有电池不行，还得有人"看护"和"转换"。两个最重要的设备：

**① BMS（电池管理系统）—— 电池的"保姆 + 护士"**

- 它紧贴着每一节电芯，实时量**电压**、量**温度**；
- 它做"**均衡**"：让同一个包里的电芯电压尽量一致（否则一包的性能会被最差的那节拖垮）；
- 它通过 **RS485 串口**把所有这些读数对外上报。
- 类比：每一节电芯都配了一个"体温计 + 血压计"，BMS 就是汇总所有读数的护士，定期把体温表交给上级。

**② PCS（功率变换系统）—— 电池的"翻译官 / 充电桩"**

- 电池里存的是**直流电（DC）**，但电网送来 / 要送走的是**交流电（AC）**；
- PCS 在中间做双向转换：充电时把电网交流变直流灌进电池；放电时把电池直流变交流送回电网；
- 它通过**以太网**上报功率、频率、运行状态。
- 类比：就像充电宝里那个"充电 / 放电电路"，只不过功率是**兆瓦级**（百万瓦）。

> 除了这两类，现场还有**关口电表**（计量充放电量）、**液冷空调 / 消防**（给电池降温、保安全）等辅机，它们也都要被监控。

### 0.4 我们到底在盯哪几个数？

所有上报数据里，最关键的就这么几个。记住它们，就懂了系统在防什么：

| 指标 | 是什么 | 为什么重要（盯它的理由） |
|------|--------|------------------------|
| **电压** | 每节电芯的电势 | 过高→可能过充报废；过低→可能过放损坏 |
| **温度** | 每节电芯的体温 | **过高→可能热失控、起火**，所以温度告警是安全红线 |
| **SOC** | 剩余电量百分比（像手机电量） | 运维要知道"还剩多少电能放" |
| **SOH** | 电池健康度（像人的"体力年龄"） | 慢慢下降，老了就该维护 |
| **均衡状态** | 一包里电芯电压是否一致 | 不一致＝有"坏电芯"，是老化早期信号 |

> 一句话点题：**温度、电压这些数，单个看无害，但"某个电芯悄悄升温"就是事故的苗头**。所以监控的核心价值 = 在千万个数字里，第一时间抓住那个"不对劲"的。

### 0.5 一句话回答：为什么需要"上位机"？

把上面拼起来：

> 一个电站有**上万节电芯**，每节每 **100 毫秒**就报一次电压、温度。没有任何人能同时盯住这么多数字。**"上位机"就是那块屏幕软件**——它把这一大堆原始读数，变成人一眼能看懂的总览图、曲线，并在某个电芯温度超标时**立刻报警**。

所谓"上位机"（相对"下位机"= 电池/BMS 这些底层设备而言），就是**运行在电脑上、专门用来监视和控制这些设备的软件**。本项目做的，正是这样一块"储能电站的监视大屏 + 数据中枢"。

### 0.6 一张总图：从一节电池到一块屏幕

```
  [电芯 Cell] ──量测──▶ [BMS] ──RS485串口──┐
  [PCS] ──以太网──┐                        │
  [电表/辅机] ────┤                        ▼
                  └──▶ [EnerSentry 上位机] ──▶ 屏幕：总览 / 曲线 / 告警
                          （解析·汇聚·报警·存历史）        └─▶ 历史数据库
```

记住这条链路，后面所有功能模块都是在这条链路上"长"出来的。

## 一、这个项目是什么

**一句话**：EnerSentry 是一台「储能电站的本地监控大屏 + 数据中枢」软件——它运行在电站现场的工控机或监控电脑上，负责把几十台 BMS、PCS、电表、辅机上报的实时数据，变成运维人员一眼能看懂的**总览、曲线、告警和报表**。

用一个类比建立直觉：它就像储能电站的「**仪表盘 + 黑匣子 + 报警台**」三合一。

| 维度 | 说明 |
|------|------|
| **产品定位** | 储能电站**站端监控上位机 / 本地 SCADA-HMI**，位于设备层之上、云端与 EMS 之下（做监视与本地分析，不直接下发功率调度指令） |
| **控制能力** | 以**只读监视为主**；同时具备本地紧急控制能力（手动排风/液冷、告警复位、紧急切断等站端安全操作），但严格遵循工业级 **SBO（Select Before Operate，预置-选择-执行双重确认）** 与权限校验，防止误操作 |
| **气质对标** | 工业组态软件 KingSCADA / iFIX / WinCC 的「站端监控」能力——命名与产品形态一眼像真实工业软件，而非课程作业 |
| **命名逻辑** | Energy（储能）+ Sentry（哨兵，突出「实时监视 + 告警防线」的产品定位） |
| **英文副标题（可写进简历）** | *BESS Supervisory & High-Frequency Acquisition System* |
| **核心使命** | 把现场「串行字节流」变成人能决策的「信息」——解决工业软件里最经典的那一公里：**从设备到界面** |

> 一句话区分定位：商业组态软件把链路全封装好了，而本项目的价值恰恰在于**亲手把从字节到像素的完整技术链路打穿、做扎实**，因此每一层都经得起追问。

### 1.1 量化性能指标（设计基线）

工业上位机项目最忌「空谈高频/海量」。以下为本项目的**设计性能基线**——每一项都可用模拟器压测产出真实数字来验证，而非纸面口号：

| 维度 | 指标参数 | 说明 |
|------|---------|------|
| **测点规模** | 单站支持 **10,000+** 实时测点 | 含 16 簇电池，每簇约 640 单体电压/温度点，加上 PCS、电表、辅机状态量 |
| **采集频次** | 核心 BMS 极速包 **100ms/帧**；辅机/电表 **1s/帧** | 高低频混合采集，BMS 快包走独立高频通道 |
| **界面刷新** | 高频数据刷新时 UI 保持 **60 FPS** 顺滑 | 同屏多曲线滚动不卡顿；**CPU 占用率 < 15%**（单核工控机可用） |
| **告警响应** | 从底层解析到声光告警与弹窗，端到端延迟 **< 100ms** | 告警判定不因界面渲染而阻塞——安全生命线 |
| **历史落库** | 写入吞吐量达 **5,000 点/秒** | 持续稳定写入不丢帧；历史曲线 **24 小时数据加载 < 1 秒** |

> 这些数字不是凭空给的，而是基于储能站真实规模与工业监控通用要求推导出的设计基线。它们把「高频」「海量」从形容词变成了**可验证的工程承诺**——这正是面试官区分「做过」与「做扎实」的分水岭。

## 二、为什么这个行业需要它（行业背景）

> 本章假设读者已读过第零章。下面用更"工程化"的语言复述一遍结构，并点出痛点。

### 2.1 电站的层级结构（回顾）

```
储能电站
 ├── 电池舱 × N
 │    └── 电池簇 Rack × M ── BMS 从机 (RS485 / Modbus RTU)
 │         └── 电池包 Pack × K
 │              └── 电芯 Cell × 100+   → 单体电压 / 温度
 ├── PCS 功率变换系统 × P   (Modbus TCP，以太网)
 ├── 关口电表 / 并网柜        (Modbus TCP)
 └── 辅机：液冷空调、消防、环境监测 (Modbus RTU / TCP)
```

**规模感**：一个电站动辄上万测点——数百个电池簇 × 每簇几十个 Pack 级测点 + 上千个 Cell 级测点，再加上 PCS、电表、辅机的功率与状态。

### 2.2 数据从哪里来、怎么来

| 设备 | 通信方式 | 上报内容 |
|------|---------|---------|
| **BMS（电池管理系统）** | RS485 串口 / Modbus RTU；**底层快包接口预留 CAN 总线直连** | 单体电压、温度、SOC、SOH、均衡状态、告警字 |
| **PCS（功率变换系统）** | 以太网 / Modbus TCP | 有功/无功功率、电压/电流/频率、运行模式、故障字 |
| **关口电表** | 以太网 / Modbus TCP | 充放电电量、功率、电能质量 |
| **液冷/空调/消防等辅机** | RTU 或 TCP | 温度、流量、阀门状态、消防告警 |

> **关于 CAN 总线**：在真实储能站中，BMS Pack/Rack 内部大量使用 **CAN 总线**（如 CANopen / SAE J1939），而非仅仅是 RS485。现场常见的是 CAN 卡（如周立功 CAN 卡、Linux SocketCAN）或 CAN 转 Modbus 网关。因此本系统的接入层设计为：**BMS 上层汇总走 Modbus RTU/TCP，底层快包接口同时预留对 CAN 总线（SocketCAN / ZLG CAN）的直连解析能力**。这不仅更贴合真实储能站硬件生态，也让协议接入层的扩展性经得起追问。

关键点：**设备上来的不是「温度 32℃」这种人类可读的信息，而是 Modbus 寄存器里一串 16 位整数/浮点**（或 CAN 帧中的打包二进制）。要变成屏幕上的曲线和告警，中间有一整条解析、组织、呈现的链路——这正是上位机软件的职责。（见 0.6 总图）

### 2.3 现场的真实痛点（为什么不能随便写个界面）

| # | 痛点 | 工业现实 | 对系统的要求 |
|---|------|---------|-------------|
| **P1** | **测点密度极高** | 单站轻松上万测点；BMS 快包 10~100ms 级上报 | 高频接收不丢帧、界面不卡顿 |
| **P2** | **多协议多链路并存** | 串口 RTU（BMS/辅机）与 TCP（PCS/电表）并存；485 是半双工总线；BMS 底层还存在 CAN 总线（CANopen/J1939） | 需要合理的多链路接入与调度，协议层预留 CAN 直连扩展 |
| **P3** | **通信环境恶劣** | 485 受变频器干扰产生 CRC 错、乱码；网络抖动导致断链 | 健壮的协议处理 + 自动重连 + 通信质量统计 |
| **P4** | **告警是安全生命线** | 电芯过温漏报可能诱发热失控事故 | 告警不能因界面卡顿而延迟，且须留痕 |
| **P5** | **历史数据既要写得快又要查得快** | 秒级采样一天就是千万行级；运维要回看「上周三下午的簇温曲线」 | 高效写入 + 快速历史查询 |
| **P6** | **开发期拿不到真设备** | 上位机常先于硬件到位就要开发联调 | 需要完整的软件仿真与故障注入体系 |

这些痛点共同决定了：它不是一个「读个数画个图」的小工具，而是一个要求**高并发、强健壮、可持久化、可验证**的工业级系统——也正是 C++/Qt 上位机岗位最典型的真实场景。

## 三、让人一眼看懂：四个真实业务场景

> 读到这里可能还是抽象。下面用四个场景，描述「用户在这个系统里到底在干什么」。术语若忘了，回看第零章。

### 场景一：日常巡检 —— 「一眼看清整站状态」

> 周一早晨，运维工程师老李打开 EnerSentry。

- 进入**电站总览页**：一张电站缩略图，N 个电池舱以卡片铺开，每张卡片显示该簇 SOC（电量百分比）、总压、最高/最低温度、健康色（绿/黄/红）。
- 发现 3 号舱颜色发黄，老李**点进该舱 → 看到下属电池簇 → 再钻取到某个电压异常的电池包**，直接在界面上定位到「Pack-07 里第 23 节电芯，电压明显比同包其他电芯低——这通常是那节电芯老化的信号」。
- 整个过程**不用一句代码、不用翻寄存器点表**，全是鼠标点击的层级钻取。

**系统在这时提供了什么**：把上万个测点组织成「站 → 簇 → 包」三级结构（对应 0.2 的四层嵌套），用颜色和仪表盘做异常可视化，让人从「海量数字」里一眼抓到异常点。

### 场景二：深夜过温告警 —— 「从报警到定位只要几秒」

> 凌晨 2 点，系统发出严重告警蜂鸣。

- 屏幕上**告警中心**弹出一条红色告警：「Rack-05 最高温度 58.3℃，超过 55℃ 阈值，已持续 3 秒」。（温度为何是红线？见 0.4）
- 老李点击「**确认**」，蜂鸣停止；再点「**查看现场**」，系统自动调出该簇告警**前后 30 秒的高频数据曲线**（黑匣子快照），他看到温度在 10 秒内从 52℃ 爬升到 58℃ 的完整过程。
- 同时，历史趋势页显示该簇近 24 小时温度一直在缓慢上升——判断为**液冷流量不足**而非电池本身故障，于是派单检修空调，而非盲目更换电池包。

**系统在这时提供了什么**：分级告警、告警确认闭环、以及「告警 + 现场数据快照 + 历史趋势」三位一体的定位能力——让告警从「响一下」变成「说得清原因」。

### 场景三：周报与事故回溯 —— 「把上周三那根温度曲线调出来」

> 周五，老李要给主管出一份运行周报。

- 在**历史趋势页**输入时间区间「上周三 00:00–24:00」，勾选「全部电池簇最高温度」。
- 系统秒级返回曲线，老李**滚轮放大**到「14:00–15:00」区间，曲线自动变清晰；他发现 14:30 有一根**温度尖峰**（恰好是当时一次大功率调频放电），于是导出该段 CSV 附进周报。
- 整份周报的数据，全部来自系统长期自动落库的历史采样。

**系统在这时提供了什么**：海量历史数据的快速查询、缩放回放与导出——把「运维凭记忆写报告」变成「数据自己会说话」。

> **为什么历史库没被高频数据撑爆？——数据生命周期与降采样策略**
>
> 如果按 100ms 高频全量落库，16 簇电池一天就会产生数亿条记录，本地 SQLite/MySQL 瞬间爆满。因此系统采用**分级持久化**策略：
>
> | 层级 | 存储 | 保留策略 | 用途 |
> |------|------|---------|------|
> | **L1 快照库** | 内存 / 高频缓存 | 保留最近 **1 小时** 100ms 全量高频数据 | 实时盯盘；发生告警时自动将**前后 30 秒**数据锁定为「黑匣子快照」，供事故回放 |
> | **L2 历史库** | 本地持久化存储 | 常态数据经 **1s / 5s 聚合降采样**（保留 Max/Min/Avg）后落库 | 长期趋势分析、周报回溯、一致性分析——兼顾精度与存储空间 |
>
> 这样一来：日常趋势看 L2 降采样数据（一天仅数百万行，可存数月），事故回放看 L1 黑匣子快照（高频全量、毫秒级还原）。**高频不落全量、低频不丢趋势**——这是工业监控存储设计的核心取舍。

### 场景四：开发期无设备联调 —— 「用软件模拟器把整站跑起来」

> 项目刚启动，现场设备还没发货，但开发不能等。

- 工程师启动内置的**软件设备模拟器（Mock Device）**，它在一个独立程序里同时扮演 16 个 BMS 从站 + 4 台 PCS + 1 个电表，通过虚拟串口和以太网「假装」成真实设备，按真实 Modbus 协议回包。
- 更关键的是，模拟器带一个**故障注入控制台**：工程师点一下「注入电池过温」，模拟器就按物理规律把某 Pack 温度往上推 → 上位机应声弹出严重告警；点一下「随机断线」，链路状态机自动重连。
- 整个系统的协议、告警、存储、曲线，在没有一块真电池的情况下就被**完整验证**了。

**系统在这时提供了什么**：一套不依赖硬件的「设备仿真 + 故障注入」能力，让系统在上线前就被反复锤炼——这是工业软件开发的基本功，也是本项目刻意设计的能力。

## 五、系统能做什么（功能全景）

下面按模块说明系统对外提供的能力（功能视角，而非内部实现）。

```
┌──────────────────────────────────────────────────────────┐
│                      EnerSentry 主界面                     │
├────────────┬────────────┬──────────┬──────────┬───────────┤
│ ① 电站总览 │ ② 实时曲线 │ ③ 告警中心│ ④ 历史趋势│ ⑤ 参数配置 │
├────────────┴────────────┴──────────┴──────────┴───────────┤
│ ⑥ 通信诊断  │  ⑦ 设备模拟器（独立程序 + 故障注入控制台）      │
└──────────────────────────────────────────────────────────┘
```

| # | 模块 | 它做什么（用户视角） |
|---|------|---------------------|
| **① 电站总览** | 系统的「首页」 | 站 → 簇 → 包三级钻取（对应 0.2 层级）；SOC 仪表盘、温度/电压概览、异常色块；让人一眼掌握整站健康度 |
| **② 实时曲线** | 数据的「动态心电图」 | 多条曲线同时滚动刷新（电压/电流/温度/SOC 等），用于盯盘与瞬时异常观察 |
| **③ 告警中心** | 安全的「报警台」 | 三级告警（提示/一般/严重）分级呈现、声光提示、操作员确认闭环、告警历史查询；每条告警可一键关联「现场快照」 |
| **④ 历史趋势** | 数据的「录像回放」 | 任意时间段查询、曲线缩放回放、CSV 导出；用于周报、事故回溯、电池一致性分析 |
| **⑤ 参数配置** | 系统的「说明书录入」 | 设备/从站/寄存器点表配置、轮询周期、告警阈值规则——**点表驱动，不硬编码**，换电站不改代码 |
| **⑥ 通信诊断** | 链路的「体检报告」 | 实时显示每条串口/TCP 链路的状态、请求数/超时数/CRC 错数/平均往返时延、通信质量百分比 |
| **⑦ 设备模拟器** | 没有真设备时的「假电站」 | 独立程序模拟整站设备（BMS/PCS/电表），按真实协议回包；带故障注入控制台，可制造过温、断线、乱码等异常 |

> 这七个模块覆盖了工业监控上位机的标准能力面：**监视（总览/曲线）→ 报警（告警中心）→ 追溯（历史趋势）→ 配置（点表/阈值）→ 运维（通信诊断）→ 自测（模拟器）**，是一个完整闭环。

### 5.1 工业级 HMI 交互亮点

除了上述功能模块，系统在交互层面刻意对标真实工控室的运维习惯：

**① 本地手动控制与 SBO 双重确认**

上位机虽以只读监视为主，但站端运维必须具备本地紧急控制能力（手动开启排风/液冷、告警复位、紧急切断等）。所有控制下发严格遵循工业级 **SBO（Select Before Operate，预置-选择-执行）** 流程：

```
操作员发起指令 ──▶ ① 选择目标设备（Select）
                         │  系统校验权限 + 设备可控状态
                         ▼
                   ② 预置指令待确认（Armed，带 5s 倒计时窗口）
                         │  操作员二次确认（Operate）或取消
                         ▼
                   ③ 正式下发执行 ──▶ 全程操作留痕（谁/何时/做了什么）
```

> SBO 的本质是「**防止误操作**」——选择与执行分两步、中间留确认窗口，即使手抖点错也不会立即生效。这是电力/工业控制的铁律，也是面试中体现「懂工业安全规范」的关键加分点。

**② 多屏 / 大屏适配**

支持工业控制室常见的双屏/多屏拓展显示：

- **主屏**：电站总览 + 告警中心——运维盯盘的核心视野；
- **副屏**：实时趋势曲线 / 历史回放——辅助分析与对比。

窗口可独立拖拽到副屏，各屏独立刷新、互不阻塞，适配 7×24 小时值守场景。

**③ 暗色工控主题（Dark Theme）**

主打深色低刺激 UI，适应控制室长时间盯盘需求：

- 深色背景降低屏幕眩光与视觉疲劳；
- 告警色（**红 = 严重 / 黄 = 一般**）高对比度凸显，确保告警在暗色环境中一眼可见；
- 遵循中国工业监控惯例：**红色 = 异常/告警，绿色 = 正常**。

**④ RBAC 权限管理**

区分三级操作权限，确保「看得见的不能乱改、能改的有迹可循」：

| 角色 | 权限范围 |
|------|---------|
| **操作员** | 查看总览/曲线/告警，确认告警，导出报表 |
| **工程师** | 操作员全部权限 + 修改点表配置、告警阈值、通信参数 |
| **管理员** | 工程师全部权限 + 用户管理、系统配置、控制权限分配 |

> 所有控制操作（尤其 SBO 下发）均需权限校验 + 操作日志留痕，满足工业审计可追溯要求。

## 六、系统边界与部署形态

### 6.1 部署形态

- **单机部署**：运行在电站现场的工控机/监控电脑上，通常 Windows（现场常用）或工控 Linux（Ubuntu）双平台。
- **本地优先**：数据以本地落库为主，不依赖外网；这是站端系统「断网也能看、掉电也不丢」的基本诉求。

### 6.2 接入对象

系统对接的两端：

- **真实设备**：现场 BMS（RS485/RTU）、PCS/电表/辅机（以太网/TCP）。
- **软件模拟器**：本项目的「假电站」——在开发、演示、测试阶段替代真实硬件，通过虚拟串口 + 以太网提供与真实设备**字节级一致**的协议回包。

### 6.3 数据流向（一句话版）

```
设备字节流 → 协议解析 → 实时数据中枢 → 分发给 [界面呈现 / 告警判定 / 历史落库]
```

（数据在内部的并发组织、缓冲、双库分工等，属于技术实现篇，此处不展开。）

### 6.4 什么在范围之外（同样重要）

为避免项目无限膨胀，明确**不做**以下事情：

- 不替代 EMS/调度系统去做电网级功率调度与控制下发——**系统以只读监视为主**；
- 但在站端运维安全层面，系统**具备本地紧急控制能力**（排风/液冷/复位/急停），所有控制操作严格遵循 **SBO 双重确认 + 权限校验 + 操作留痕**，这是上位机必须具备的安全能力，而非越界；
- 不做云端大平台与多站集中管控（本系统聚焦单站站端）；
- 不追求覆盖 Modbus 之外的全部工业协议（如 OPC UA、Profinet），但架构上预留扩展点（含 CAN 总线直连扩展）。

> 清晰的范围边界，本身就是工程成熟度的体现——面试官更信任「知道自己不做什么」的人。而「只读为主 + SBO 紧急控制」的定位，恰好区分了「站端监视上位机」与「电网调度 EMS」的职责边界，体现了对工业安全分层的理解。

## 八、附录：关键术语速查

| 术语 | 含义（一句话） |
|------|--------------|
| **电芯 Cell** | 最小的锂电池单体，如磷酸铁锂 3.2V，一切的起点（见 0.2） |
| **电池包 Pack** | 把几十~上百节电芯串并联做成的"电池模块" |
| **电池簇 Rack** | 把十几个电池包叠成的高柜 |
| **电池舱 Container** | 装几簇 + 空调消防的集装箱，一个电站有多个 |
| **BESS** | Battery Energy Storage System，电池储能系统 |
| **BMS** | Battery Management System，电池管理系统，量电压/温度/做均衡，电池的"保姆"（见 0.3） |
| **PCS** | Power Conversion System，功率变换系统，电池与电网之间的直流/交流双向转换"翻译官"（见 0.3） |
| **SOC / SOH** | 电池剩余电量百分比 / 电池健康度百分比 |
| **RS485 / RTU** | 工业串行总线 / Modbus 在串口上的传输模式（半双工，一问一答） |
| **Modbus TCP** | Modbus 跑在以太网上的模式（全双工，按 MBAP 头拆帧） |
| **SCADA** | 数据采集与监视控制系统，工业监控的统称 |
| **HMI** | 人机界面，操作员与设备交互的软件/硬件 |
| **上位机** | 相对"下位机（PLC/设备）"，指运行监控软件的计算机 |
| **点表** | 把「设备寄存器地址 ↔ 业务含义（如 Rack-05 温度）」对应起来的配置表 |
| **告警迟滞/同源抑制** | 防告警风暴的两招：临界值带回差、同类故障只报一条 |
| **黑匣子快照** | 告警发生时自动存下的前后高频数据，用于事故回放定位 |
| **CAN 总线** | Controller Area Network，工业/汽车领域高速串行总线；储能 BMS Pack/Rack 内部大量使用 CAN（如 CANopen / SAE J1939） |
| **SocketCAN** | Linux 内核原生 CAN 驱动框架，使 CAN 设备可像网络接口一样编程访问；Windows 侧常用周立功（ZLG）CAN 卡驱动 |
| **SBO** | Select Before Operate，工业控制「预置-选择-执行」双重确认流程——选择与执行分两步、中间留确认窗口，防止误操作 |
| **降采样** | 将高频数据按时间窗口聚合（保留 Max/Min/Avg）后以低频落库，兼顾长期趋势精度与存储空间控制 |
| **RBAC** | Role-Based Access Control，基于角色的权限控制——区分操作员/工程师/管理员，控制操作需权限校验 + 留痕 |
| **L1/L2 分级存储** | L1 = 内存高频快照（1h 全量 + 黑匣子）；L2 = 降采样历史库（长期趋势），是工业监控存储设计的核心取舍 |
